# Canonical local wallet and work income

All local Game Room and Pet consumers use the economy owner's `economyLocalWallet` read service and the same immutable local wallet. The balance is never a sum of source balances. Account identity is `codex:` plus SHA-256 hex of `JSON.stringify([instanceId, HostOpaqueSubject])`; names are presentation only. Ledger source labels come from authoritative agreement service IDs. A remote game source that cannot settle with this loopback wallet does not support Token play.

## Actual local work issuance

Every 10,000 eligible input plus output tokens earns one coin. There is no total budget, daily budget or per-account daily cap. Cached input and reasoning are already included; do not add them again. The trusted Host uses its durable classified work-v2 projection: known root work only, with Host game tasks, forks/subagents and unknown sources excluded. This is local partial coverage, not a cloud bill or an OpenAI attestation.

The wallet calls HTTP/v3 `submitWorkUsage` with the provisioned binding and optional `baseline: true`. It cannot submit an account, amount, token count, cursor or snapshot. The Launcher reads actual usage and the signed-in Native identity, signs the observation using its provisioned Ed25519 key and validates the server's signed result. The service requires a pinned Host key, exact origin/source/instance/audience, a fresh once-consumed challenge and an immutable Native subject. Ordinary game/user bearer credentials cannot issue work income.

The service derives income from its durable frontier and remainder, atomically increases recorded supply and the user's balance, appends a `work-income` ledger entry, and records an idempotent receipt. First observations, new epochs, new Host leases and observation gaps over 15 seconds establish a baseline. Baselines only move forward and forfeit missed income; they cannot reset counters or revisit a retired epoch. A five-second owner heartbeat maintains continuity. Exact receipt retries and alternate window partitions cannot issue overlapping income. Exact integer overflow fails closed; it is a storage limit, not an issuance budget.

## Explicit local trust and automatic account connection

Provision two managed trust entries for the wallet's actual owner: `source-account` and `work-income`, with the same canonical economy origin and instance. The source IDs are independently configurable; both default to `economy-local`. Host signing keys remain in keychain. Each server trust file contains binding, Host public key and server private key and must be a regular 0600 file. Do not place it in renderer or plugin configuration. This is an explicit local trust grant, never automatic loopback discovery.

The service accepts their comma-separated file paths through `ECONOMY_MANAGED_TRUST_FILES`. The listener must match the pinned origin. No trust files means these routes are disabled. A verified Native identity may create a zero-supply local instance and a zero-balance user wallet; it does not consume sponsor money or grant genesis credit. Signed source-account results contain a game-specific user session, which the Launcher strips and stores behind an opaque Host connection. Work results return wallet identity and receipt without a bearer.

Configure `localEconomyOrigin`, `localEconomyInstanceId`, `localEconomySourceId` and `workIncomeSourceId` on `wallet/src/wallet.tsx`. A configured origin triggers automatic Native identity connection on activation. HTTP/v1/v2 continue to support existing manual SDK sessions, but cannot silently replace managed login or issuance. `usage.read` is required. No npm publishing or running service is started by this source candidate.

## Producer retirement and uncertain requests

Keep `legacyPetHistory: 'requires-retirement'` when Pet may have been used. Replace all old producers through Host lifecycle, permanently stop new Pet observations and recover only exact existing pending events using their original source, identity, amount and idempotency key. Preserve the original document and ledger. Current Pet must publish live same-scope, pending-free retirement proof. The provider exposes `subscribeInvalidation(listener)` and publishes terminal invalidation on disposal. The wallet immediately downgrades and notifies its income subscribers. The wallet checks it on every observation and again after persisting its intent; absence is not no-history evidence. An explicit `never-enabled` deployment declaration is allowed only for a genuinely new profile and is persisted. It is human evidence, not Host-certified history.

An unresolved old finite wallet intent also blocks cutover. The new owner persists a CAS intent containing identity and request state, never a caller-chosen amount. An uncertain reply leaves that intent intact with an explicit settled-failure status. Active intents are never taken over merely because time elapsed. Only the original owner can publish failed/retired after a trusted SDK terminal reply or before any request started. A bridge/transport `host-unavailable`, an unknown thrown error, stale generation, owner retirement or a crash is not a terminal fact. If these prevent publishing termination evidence, retain the active record and block takeover pending explicit reconciliation. Its next request conservatively baselines; server frontier and receipt prevent duplicate issuance. Do not copy old earned totals, remainders or test funds into the new wallet.

Readonly `incomeStatus` and `subscribeIncome` expose income readiness separately from wallet balance. Provider replacement immediately downgrades the getter; owner disposal publishes a final unavailable state. These projections cannot mutate money. The legacy finite reward grant API and `LocalWorkIncome` engine remain available for their established sponsor use, but are not this wallet's formal work-income route.

## Native account switches

Work scope is based on Host profile and Codex home, not on the Native subject. A scope already bound to account A cannot be reassigned to B. Native B may connect to a separate zero-balance account, but work issuance for that existing scope is blocked. The canonical wallet owner document also preserves A and rejects silent replacement. Restore the original account for the original scope, or configure a separate genuine profile/scope. Do not rewrite bindings, copy balances or remint history to bypass this restriction.

## Genuine first installation with Pet

`LegacyWorkRetirementReadService.currentProducer()` separates current runtime from original history. It returns live disabled producer contract, generation and current classified work scope, plus exact original record status (`missing`, `present`, `unavailable` or `invalid`). It creates no history document or retirement schema/revision. Only an immutable explicit human `legacyPetHistory: never-enabled` declaration, a live same-generation/scope disabled producer and exact `missing` may enter the initial baseline. `present`, `invalid` and `unavailable` never use this shortcut. Retirement-required profiles still need the actual schema-2 pending-free original record. Once this wallet has seen a provider, removal cannot revert to the initial absence allowance; a new live provider must be validated. Every read, subscription, send and readiness publication is fenced by provider identity and generation.

A provider observed through any readiness getter, verification or operation fence permanently disables absence-only `never-enabled` fallback for that owner. Removing even an unverified provider cannot restore absence eligibility. Pet preserves explicit Host `missing` separately from loaded null or invalid/unavailable history.

## Explicit correction of a conservative default

`requires-retirement` is a conservative policy, not proof of prior Pet history. A user-confirmed genuinely unused profile may correct that default through the same Wallet owner and profile, retaining the canonical wallet and original document. This never happens because Pet or a document is missing. Keep the correction unset until the user explicitly confirms true history.

Set `legacyPetHistory: never-enabled` together with `legacyPetHistoryCorrection: { action: confirm-never-enabled, statement: <explicit human declaration> }` through normal Host configuration. The statement must be nonempty, at most 1000 characters and stable across recovery. The immutable constructor captures it. The owner checks original local cursor/remainder/earned/event/pending, actual same-scope disabled Pet original-record projection when present, and exact absence of its usage issuance document. Any existing/invalid/unavailable cutover or original work history blocks correction. Original Pet missing is not independently sufficient; the positive human declaration is mandatory.

The owner first CAS-persists a pending manual correction without changing the old policy. Its own opaque source-account session calls `/v1/income/history-declaration` (no arbitrary target account, profile, tokens or amount). Server audited begin/confirm transactions require an unused zero wallet, no account ledger, work bindings/frontiers/epochs/leases/receipts. Pending server audit blocks trusted work provisioning/issuance, avoiding a status-read/CAS race. The owner keeps the conservative policy while saving pending audit fields, confirms the server receipt, then performs a producer-fenced CAS of policy and terminal evidence. Old document fields and all accounting remain retained. New observations baseline conservatively after completion.

Unknown replies or closure leave pending records and block income; they never authorize a clock takeover. Resume with the same explicit action and original statement. A confirmed server receipt may finalize its pending local record without recreating past tokens, even after another authorized owner has begun work following confirmation. To cancel an unfinished operation, use `legacyPetHistory: requires-retirement` and correction `{ action: cancel, statement: <same original statement> }`. Explicit server cancellation and local CAS restore the conservative policy and retain the audit. Confirmed declarations cannot be cancelled. Existing accounting/cutover cannot be silently reopened. This is a new supported source workflow, not an operation already executed against the current profile.

Producer checks run after every final document read and non-cancellation server reply, immediately before confirmation and each policy CAS, and after CAS completion. An invalid provider leaves conservative pending policy while the server receipt may be pending or confirmed; it is not a proof of no server effect. Recovery verifies a current producer before looking up an existing confirmed receipt. If a final CAS already committed before invalidation is observed, its terminal receipt is retained and income is blocked; no terminal state is downgraded.
